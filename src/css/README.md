# `src/css/` — the 3.x stylesheet

Plain CSS. No Sass, no Bootstrap, no preprocessor of any kind.

Everything in here reads design tokens and nothing else. The two places that
genuinely need iteration — the variant × colour matrices and the utility layer —
are generators that read the token model directly, so neither can drift from it.

> `src/style/` — the 2.x Sass tree — and the `bootstrap` dependency are both
> **deleted**. This is the only stylesheet. The 38 components still emitting
> Bootstrap class names therefore render unstyled until they are ported; run
> `npm run css:audit` for the list.

## 2. Cascade layers

```css
@layer df.tokens, df.reset, df.base, df.components, df.utilities;
```

That one line in `layers.css` does most of the work:

- **A consumer's own CSS is unlayered, and unlayered styles beat every layer**
  regardless of specificity. So a client overrides anything Dynamic ships with a
  plain selector — no `!important`, no specificity arms race. This is what
  retires `_shame.scss` and `$enable-important-utilities`.
- **Within Dynamic, later wins**: a utility beats a component, a component beats
  an element style. So utilities need no `!important` either.

Layer *order* is fixed by where a layer is first named, which is why that
statement has to come first in the bundle — and why the source files can then be
concatenated in any order without changing the outcome.

## 3. The component pattern

Every component block declares **local custom properties** and styles itself
entirely through them. A generated selector per variant × colour fills them:

```css
/* components/button.css — hand-written */
.df-button {
  --df-button-bg: transparent;
  --df-button-fg: var(--df-fg-default);
  background-color: var(--df-button-bg);
  color: var(--df-button-fg);
}
.df-button:where(:hover, .df-hover) {
  background-color: var(--df-button-bg-hover);
}

/* generated by scripts/css/build-variants.mjs */
.df-button[data-variant="solid"][data-color="primary"] {
  --df-button-bg: var(--df-role-primary-base);
  --df-button-bg-hover: var(--df-role-primary-base-hover);
  --df-button-fg: var(--df-role-primary-on-base);
}
```

Three things this buys over 2.x's one-class-per-combination:

1. **State lives in one place.** `:hover` reads `--df-button-bg-hover`, so the 32
   variant × colour selectors never mention a state.
2. **The slots are the documented override surface.** A client retunes one
   combination with that same selector, or retunes the role and moves everything
   at once.
3. **Those ~350 combinations stop being globals in `:root`**, which is a large
   part of why the 2.x stylesheet is 1.2 MB.

### Markup contract

`.df-block` plus data attributes for variants and state:

```html
<button class="df-button" data-variant="soft" data-color="danger" data-size="sm">
  <span class="df-button-label">Pay</span>
</button>
```

Data attributes rather than more classes because the axes map 1:1 onto React
props and onto custom-element attributes, so both renderers share one selector
and neither needs classname-assembly logic.

### Naming

**Everything is hyphen-separated.** A child part reads as a longer name, not as
a separate kind of token:

```
.df-card            block
.df-card-header     part of it
.df-button-label    part of it
```

An earlier draft used BEM's `__` for the element separator (`.df-card__header`).
It is dropped: this codebase and the 2.x stylesheet it replaces are
hyphen-only throughout (`card-body`, `btn-group`, `input-group`), and mixing two
separators means every author has to remember which one a given part uses.
`.stylelintrc` enforces `^df(-[a-z0-9]+)+$`, so an underscore fails the lint.

The trade-off is real and accepted: with one separator, `.df-input-group` is
ambiguous between "the input-group block" and "the group part of input". The
answer is that it is a block, and the component's CSS file is where that is
settled.

### Specificity discipline

State selectors within a component are all kept at the **same** specificity, so
source order alone decides, and they are ordered by increasing priority.

`:where()` contributes zero specificity and `:is()` contributes its most
specific argument — that is what makes it possible. Written the obvious way,
`.df-input:hover:not(:disabled)` is `0,3,0` and `.df-input:focus` is `0,2,0`, so
hovering a focused field would paint the hover border over the focus border no
matter how the rules were ordered. `stylelint`'s `no-descending-specificity`
catches this; it is not a style nit.

```
  reset.css               replaces Bootstrap's Reboot. Normalisation only.
  base/
    document.css          page ground, colour-scheme handshake, sr-only

    list.css     progress.css alert.css   card.css
```

Source order is declared explicitly in `scripts/css/build.mjs`, not globbed: the
cascade is load-bearing and a directory listing is not a design decision.

## 5. Build and checks

```bash
npm run css            # tokens -> build -> validate -> verify
npm run css:build      # assemble dist/css/*
npm run css:validate   # no dangling or malformed custom properties
npm run css:verify     # resolve the cascade; check every variant's contrast
```

`npm run css` chains `npm run tokens` first on purpose: the stylesheet reads
`dist/tokens/dynamic.tokens.css`, and building out of order emits a stylesheet
whose custom properties resolve to nothing. The build checks for the token file
and says so rather than failing silently — which it caught in practice, the
first time `alert.css` was written before its tokens were built.

### What `css:validate` protects against

Every typo 2.x shipped took one shape: a `var()` reference to a custom property
nothing defines. `--bs---bs-ref-spacer-4`, `--bs-bs-gray-400`,
`--bs-subtle-primary`, and the missing-sigil `--bs-btn-box-shadow: btn-box-shadow`
all reached the published CSS, where they resolve to nothing and the declaration
silently does not apply. A CSS parser considers all of them valid.

The check is `references − definitions-anywhere`. "Anywhere" matters: a
component's local slots are defined inside `.df-button`, not `:root`, so
comparing against `:root` alone reports every one of them as dangling.

### What `css:verify` protects against

`validate` proves nothing dangles. `verify` resolves the real bundle's `var()`
chains the way a browser would and checks the resulting colours — 128 opaque
fills across both colour modes at the moment.

That end-to-end path is where a mistake would otherwise hide: the token
validator checks `role.primary.on-base` against `role.primary.base`, but the
button uses `--df-button-fg` and `--df-button-bg`, which the generated matrix
wires to the role, which aliases a primitive. A wrong slot mapping in
`build-variants.mjs` passes every earlier check and still ships white text on a
white button.

## 6. House rules

Enforced by `.stylelintrc` for `src/css/**`:

| Rule | Why |
|---|---|
| `color-no-hex` | No literal colours. Every colour is a token — `tokens/README.md` rule B. |
| `function-disallowed-list: rgb/rgba/hsl/hsla` | Same reason. Use a token, or `color-mix()` over one. |
| `declaration-no-important` | `@layer` already gives a consumer the win. Two disables exist, both in the reset, both with a reason. |
| `selector-class-pattern` | `^df(-[a-z0-9]+)+$` — hyphens only, no `__`. |
| `custom-property-pattern` | `--df-*` public, `--_*` private to a rule. |

The config no longer extends `stylelint-config-twbs-bootstrap` — Bootstrap's own
config — anywhere. It went with the Sass tree.

## 7. Browser floor

`.browserslistrc` sets Chrome/Edge 111, Firefox 113, Safari/iOS 16.4. Those are
the exact versions `@layer` and `color-mix()` require, not a round number, and
not the `baseline widely available` query — which resolves to Safari 17.4 and
drops users this system can serve.

2.x listed Chrome 60, Safari 12 and `op_mini all`, none of which can render a
token-driven system at all.

## 8. Adding a component

1. Write `components/<name>.css`. Read tokens; declare local slots for anything
   a variant needs to change.
2. Add its tokens at `tokens/component/<name>.json` — structural only, no
   variant × colour matrix. That file is globbed, so no manifest edit.
3. Add the file to `COMPONENTS` in `scripts/css/build.mjs`.
4. If it has a colour axis, add it to `SPECS` in
   `scripts/css/build-variants.mjs` and to the `checkComponent` calls in
   `scripts/css/verify.mjs`.
5. `npm run css`. Raise the budget in `build.mjs` deliberately if needed — never
   quietly.
